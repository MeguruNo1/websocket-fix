# Computer Use 控制子进程代理排查

适用于每次操作前出现近似固定的二十多秒等待。代理继承缺失是待验证原因；不要仅凭耗时形状认定根因，也不要通过延长超时时间宣称修复。

Windows 先读 [Windows 参考](windows.md)；控制服务名称与进程环境可观察性不同于 macOS，不能硬编码 SkyComputerUseService 或把当前 shell 环境当作另一个进程的环境。下文的 macOS 工具按平台替换，同页验收原则两平台共用。

## 建立证据

1. 现场定位主应用、Codex 后端、原生 `SkyComputerUseService`、`cua_repl` 及其 `node_repl` 子进程的 PID、父子关系与启动路径。分别检查代理相关变量；只输出筛选后的变量，不输出完整进程环境。主应用或原生服务有代理，不代表 MCP 控制进程也有。
2. 确认当前系统代理与代理端口可用。检查实际使用的插件 `.mcp.json`、用户 `config.toml` 中对应 MCP 配置及当前启动器，关注 `env_vars`、`env` 和子进程环境传递。空 `env_vars` 只是线索，需结合实际环境验证。不要用 `shell_environment_policy` 修复已运行的 MCP 控制进程。
3. 用 Computer Use 工具在一个公开网页建立基线，优先采用用户指定页面，否则可用 `https://example.com`。分别记录打开页面、已加载页面的文字读取、结构读取耗时与成功状态。将网页加载、工具初始化和内容读取分开；工具计时不包括模型思考及工具调用之间的等待。
4. 按测试时间查询应用日志与可用的控制组件日志，记录具体超时、失败请求目标、重试及耗时；必要时结合进程连接和代理日志判断是否直连。已有 HTTP 成功、某条代理连接或缺少环境变量，均不足以证明这次操作的网络路径与根因。读取日志时裁剪范围并隐藏认证信息。

## 配置修正

- 用户已要求修复且证据指向控制进程代理缺失时，先备份配置到用户私有目录（macOS 700/600；Windows 私有 NTFS ACL），不放进 Git 仓库或普通诊断输出。优先采用当前版本支持的 MCP 专用环境配置，保留原有 command、args、工具设置、其他环境和超时值；已有配置做局部合并，不重复添加 TOML 表。不改应用二进制，不以修改易被更新覆盖的插件缓存作为持久方案。
- 可在实际控制服务器（现场可能名为 `cua_repl`）的 `env` 中显式设置 `HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY`，按使用库补齐小写形式及 `ALL_PROXY`。地址从当前有效代理取得，不能固定照搬历史端口。为 localhost、127.0.0.1、::1 保留直连排除，并保留用户其他合理排除项。HTTP 代理与 SOCKS 地址按实际协议填写。
- 检查该进程使用的 Node 版本与 `--help`。若支持环境代理，可加入 `NODE_USE_ENV_PROXY=1`；仅设置 HTTP_PROXY 不保证 Node 的请求库会采用它，自定义请求代理也可能覆盖默认行为。最终以实际请求路径和同页测试判断。
- 在用户 `[mcp_servers.cua_repl]` 补充 `env` 前，需确认当前版本的配置优先级与覆盖规则；配置写入后仍须验证新进程加载和跨重启生效。
- 修改后验证 TOML、检查差异，并确认新进程的实际环境。`js_reset` 可能只清空 JavaScript 会话，不能默认它会重启 MCP 服务或重新加载环境。优先使用可用的组件重载机制；若必须重启承载对话的桌面应用，说明原因并让用户重启，不擅自结束活动对话进程。

## 同页验收

重载后确认新 PID 与实际代理配置，再用同一公开 URL、同一浏览器后端和相同读取操作复测。通过受支持的 Computer Use API 计时；适量重复读取以判断是否仍有固定等待，避免混入页面导航时间。分别报告冷启动和已加载页面的读取消耗，并检查对应时间段是否仍出现原超时。

验收目标是消除每次操作前的固定二十多秒等待、保持读取成功；“几十毫秒”是用户提供的参考表现，不是所有页面的保证。curl 经代理成功只验证代理可达，不能代替 Computer Use 的文字与结构读取验收。当前进程未加载、页面未成功读取或尚未复测时，报告“配置已修正，待验收”，不报告“已恢复”。

## 常见误判与持久化限制

- 主应用、后端和原生服务有代理变量，不能证明控制进程及其子进程也有。插件中的 `env_vars` 或 `env` 需结合实际进程检查。
- `js_reset` 未更换控制服务进程时，不能将其视为配置已重新加载。读取性能改善，也不能单凭时间先后归因于代理配置修改。
- 若重启后配置项消失，应检查当前版本的配置同步与覆盖机制；来源未查明时，不断言由重启或更新删除，也不覆盖其他任务的变更。
- 某些版本由桌面应用生成并同步受管理的 Computer Use 插件配置，可能按选定变量列表构造子进程环境。不能假定手改用户配置或插件缓存会跨同步持久生效；应以当前版本实现及实际加载结果为准。
- 登录会话环境、主应用继承和受管理 MCP 的环境过滤属于不同环节；不要概括为应用每次重启都会清空全部代理。
- 找不到受支持的持久化入口时，不反复补写受管理配置，不修改签名应用或后台循环覆盖配置。若当前同页性能正常，也不应仅为缺少变量而引入额外改动。
